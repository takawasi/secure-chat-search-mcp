# 教訓と更新基準

更新日：2026-09-11。実仕様・実データ・テスト結果で前提が変わったら更新し、古い判断に従って設計を増やし続けない。

| 教訓 | 根拠・適用範囲 | 更新する条件 |
|---|---|---|
| APIの差分取得を履歴カーソルと混同しない | Chatworkの最大100件・ページング不在 | 公式に履歴ページングや新しい取得APIが提供された場合 |
| CSVに安定IDがあると決めつけない | 実CSV未受領。ID有無で整合方法が変わる | 実サンプルで列と意味が確認できた場合 |
| 検索だけでなく本文・期間・文脈も認可する | 退室後のID直接取得テスト | 入口が追加された場合は同じ認可境界を再点検 |
| 同文・同時刻を一律ハッシュで統合しない | 別投稿を消す可能性がある | 実データで安定した識別子が得られた場合 |
| 未導入の意味検索を疑似結果で装わない | 実モデル導入・未索引件数・明示的エラーを分離 | 採用モデルや導入形態を変更した場合 |
| 編集と索引更新を競合させない | 本文が変わった後に旧ベクトルを書き戻す危険 | 収集・索引の並列度を変えた場合は競合検証を追加 |
| デモ変更APIを実データ入口にしない | モード別DB、Cloud Run拒否、Webhookのモード制限 | 新しい書込経路やデプロイ先を追加した場合 |
| 公開実装の完成と顧客統合の完成を分ける | 顧客コード・認証・CSV・環境は未受領 | 実環境の検収結果が得られた項目のみ更新 |
| 説明と検証証跡を先に入口へ置く | 募集者はコードの量より実現内容と確かめ方を見たい | 実際の評価者から読順・操作上の問題が出た場合 |

検査を繰り返すだけで停滞しない。完了条件を満たした項目は閉じ、残った不確実性の最小確認へ進む。今回なら次の確認対象は実CSV・既存認証・実データ量であり、架空データの機能を無制限に追加することではない。
