# 構成と設計判断

## 利用者が得るもの

普段のChatGPTから、許可された過去の会話を検索し、いつ・誰が・どのルームで話したかを確かめられることが目的です。公開デモのWeb画面は評価用であり、顧客向けに新しいチャット画面を押し付ける構成ではありません。

```text
既存ChatGPT Business
  → 既存MCP・本人確認・allow-list・ユーザー別Chatwork OAuth
  → この検索部品（または認証済みgatewayへの呼び出し）
      → 現在参加 ∩ 承認グループ
      → キーワード／意味検索
      → 根拠と日時、必要に応じて同じルームの前後会話

履歴：管理者export → 正規化CSV＋期間マニフェスト → 原子的取込
最新：Chatwork読取API → 重複取得 → 更新・重複除去・欠損疑い
任意：Chatwork Webhook → 署名検証 → DB受信箱 → 別ワーカー反映
                              ↓
                    SQLiteまたはPostgreSQL
```

## 権限の責任

Chatwork APIが直接返したデータと違い、こちらのDBには複数ユーザーが関わる履歴が集まります。したがって、検索前にサーバー側で対象ルームを確定します。LLMが送ったルームIDやユーザーIDを、閲覧許可の証拠にしません。

`Auth.allowed_rooms` は毎回利用者の有効性を確認し、現在参加しているグループと会社の承認対象を組み合わせます。gatewayでは `/me` によるアカウント対応確認と `/rooms` による現在参加を行います。失敗したら古いキャッシュへ逃げずに停止します。同じ処理を本文取得と期間取得でも呼びます。

## 履歴と最新を無理に同一視しない

`Message.external_id` がある発言はChatwork IDで更新します。IDのない履歴には、取り込み元と行位置から内部IDを付けます。この内部IDをChatwork上のIDと偽りません。単純な「日時＋本文」ハッシュで別投稿を消すこともしません。

一対一の対応が確認できる重複は統合し、同時刻・同文の複数発言など曖昧なケースは残します。IDなし履歴の変更・削除は、宣言された完全スナップショットの範囲を差し替えて反映します。ID付き発言は、一覧から消えたことだけで削除と判断しません。

本文、編集時点、観測時点、情報源、削除フラグを分けます。古いバージョンの通知で新しい本文を上書きしません。削除を確定したら、通常検索用の本文・参照・Embeddingを消します。ただしDBバックアップやWALからの物理消去は別の運用です。

## 検索方式

最初の参照実装は、DBを増やすより、認可とデータ整合を検証しやすい構造を優先しています。SQLAlchemyのバインド変数を使い、NFKC正規化後の文字列部分一致を行います。複数の空白区切り語はANDです。日本語の分かち書きや形態素検索を実装したという意味ではありません。

意味検索は実FastEmbedモデルを任意導入します。ACLと日時などで絞った候補だけを取り出して厳密なコサイン比較を行い、文字列検索との併用はRRFで順位を融合します。未索引を件数で示し、5,000件の既定上限を超えた場合は明示的に絞り込みを求めます。長い発言のトークン切り捨てや会話単位の分割最適化は未対応です。

**PostgreSQL対応と、pgvector／日本語高速索引の導入完了は別です。** この版はJSONのベクトル保存と厳密比較です。実件数・日本語検索例・絞り込み比率を測定してから、pg_bigm／pgvector等の索引、分割、順位付けを選択します。

## MCPと期間要約

関連箇所の探索には`search`、全文確認には`fetch`、期間全体には`read_room_period`を使います。期間取得はカーソルで保存済み範囲の末尾まで進められます。ただし`stored_range_exhausted=true`は保存データの終端であって、Chatworkの全履歴取得済みという意味ではありません。

`source_history_complete`はこの版では常にfalseです。本文を命令として実行せず、出典URL、日付、情報源、確認時点を回答側へ渡します。

## 運用境界

PoCでは、取り込み・同期・Webhook反映を単一管理ワーカーで実行する構成を基本とします。API同期と索引の並列更新では行をロックして再確認しますが、大量ワーカーのスケジューラー、競合の自動再試行、分散リース、障害時の自動復旧は本番移行時の範囲です。

DBスキーマは初版v1です。`create_all`を本番マイグレーションの代わりに扱いません。顧客DBへ直接作成する前に専用DB／スキーマと移行・復元手順を設計します。
